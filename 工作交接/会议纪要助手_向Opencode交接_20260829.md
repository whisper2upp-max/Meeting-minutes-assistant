## 问题根因

配置中的 `microphone=""` 表示使用系统默认麦克风。此时 `_resolve_device("")` 正确返回 `None`，但 `_open()` 随后错误调用：

```python
dev = sd.query_devices(None)
rate = int(dev["default_samplerate"])
```

`sounddevice.query_devices(None)` 在没有 `kind` 参数时返回所有设备组成的 `DeviceList`，而不是默认输入设备。因此第二行会以字符串下标访问列表并失败。在桌面 app 中，系统声源 BlackHole 已先成功打开并触发麦克风授权弹窗，这让失败现象看起来仍像 TCC 授权竞态；实际上用户允许权限后，默认麦克风路径依然会在查询设备信息时失败。

会话产物也支持这一结论：

- 19:32、19:52 的旧会话存在 `track_mic.wav`，对应当时显式选中具体麦克风的路径。
- 20:53 至 21:06 的会话只存在 `track_system.wav`；当前配置为 `microphone=""`，均走到有缺陷的默认设备路径。
- 21:06 的 `track_system.wav` 有 12.46 秒内容，时间恰好接近 6 次麦克风重试窗口，说明 BlackHole 已正常打开，失败集中在默认麦克风打开阶段。

### 第二个根因：独立轨道长度不一致

用户在 21:37 用第一轮修复后的 app 真实录音，成功生成两轨：

- `track_mic.wav`：41.824 秒，重采样后 669,184 点，RMS 约 0.0269。
- `track_system.wav`：41.813333 秒，重采样后 669,013 点，本次为全静音。

两条设备流独立接收 PortAudio 回调，即使同时启停，也可能相差一个回调块或少量采样点。旧代码执行 `mixed + x` 时要求 NumPy 数组形状完全一致，因而报错：

```text
operands could not be broadcast together with shapes (669013,) (669184,)
```

两轨仅相差 171 点，即 16kHz 下约 10.7 毫秒，属于正常设备回调差异，不应导致整场录音失败。

### 第三个根因：WebUI 后处理相对导入层级写错

用户在 21:48 使用第二轮构建实测：

- 成功生成两条原始轨道；
- 成功混出 13.6 秒 `audio.wav`，16kHz，RMS 约 0.05；
- 随后报 `No module named 'meetingkit.webui.audio'`。

静音守卫位于 `meetingkit.webui.server`，却写成 `from .audio.base import ...`。单点相对导入会解析为 `meetingkit.webui.audio`，而正确的音频包在上一级 `meetingkit.audio`。更稳妥的做法是直接复用文件顶部已经导入的 `audio_mod`。

## Opencode出错根因分析

Opencode 前序修复正确识别了两个真实问题：缺少 `NSMicrophoneUsageDescription`，以及权限弹窗未处理完就尝试打开输入流。但修复停留在权限链路，并未继续检查“授权后每次重试实际执行到哪一步”。

具体遗漏包括：

1. 没有核对 `sounddevice.query_devices(None)` 的返回契约。
2. 没有为界面默认值 `microphone=""` 建立回归测试；现有测试只覆盖混音、配置、管线和 macOS 设备安装。
3. 新增 13 秒重试后只让同一个确定性类型错误重复发生 6 次，未用测试确认重试可以从失败恢复为成功。
4. 未把早期“显式设备成功”和后期“默认设备失败”的会话差异纳入根因分析，因而将最新失败继续归因于 TCC。
5. 原混音测试只使用时长完全相同的合成轨道，未覆盖真实独立设备必然可能出现的帧数差异。
6. 没有测试录音停止后的完整后处理分支，导致错误相对导入直到用户真机走过混音后才暴露。

## 是否属于常见低级错误

是。这属于常见的软件开发低级错误组合：

- 误解第三方 API 在 `None` 参数下的返回类型；
- UI 默认值与底层设备解析语义不一致；
- 围绕表面症状补重试，而未验证每次失败的真实异常位置；
- 缺少默认分支的最小单元测试。
- 假设两个异步设备流的数组长度必然完全相同。
- 包内相对导入层级写错，且缺少实际执行该分支的测试。

建议 Opencode 以后在加入重试前，先记录或测试单次调用的确定异常；所有界面中的“自动/默认/留空”值都必须有专门回归用例。此规则具备长期复用价值，值得加入 Opencode 的 `agent.md`。

## 修复思路

采用最小根因修复，不改变 UI、配置格式、TCC 重试次数或录音管线：

1. 在查询设备信息时显式传入 `kind="input"`，使 `device=None` 正确解析为系统默认输入。
2. 保持 `InputStream(device=None)` 的 sounddevice 标准语义，不自行缓存可能过期的默认设备索引。
3. 补齐失败资源清理，确保权限等待重试是干净、可恢复的。
4. 用 mock 测试锁定第三方 API 调用参数和失败后的 recorder 状态。
5. 混音按最长轨分配缓冲区，将短轨缺少的尾部视为静音；这样不截断任一轨，也不要求 NumPy 广播不同长度数组。
6. 增加不等长双轨测试，并用用户 21:37 的真实双轨进行重放验证。
7. 静音检查复用 `audio_mod.read_wav_mono()`，并新增从 recorder 到模拟云管线的完整后处理测试。
